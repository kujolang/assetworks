## Operating measurements

Reproduce with `KUJO_BIN=/absolute/path/to/kujo bash scripts/operating_benchmark.sh 1001`. Each distribution contains 1,001 valid records sharing a 64 KiB artifact. The skewed fixture selects IDs whose record filenames hash to shard `00`. Preparation and measurement use sibling processes. Measurement includes complete record/history/journal reconciliation, backup and an independently verified restore. Peak RSS covers the complete measurement process, not an individual phase.

At application revision `82e5a14`, on local macOS x64 with the published Kujo 1.5.0 runtime, the uniform fixture used 249 raw pages (1,998 cumulative scanned entries), with a 4 ms first page scanning seven entries. Full audit took 81,247 ms, backup 228,377 ms and restore 163,001 ms; peak RSS was 28,950,528 bytes. The backup inventory covered 2,304,439 bytes. Other tests and a container build shared this machine, so these are operating examples, not an isolated throughput comparison or service-level promise.

The skewed fixture completed with three raw pages and 3,003 cumulative scanned entries; its first page took 14 ms and scanned 1,001 entries. Full audit took 86,193 ms, backup 199,447 ms and restore 157,724 ms, with 63,315,968-byte peak RSS and 2,315,787 inventory bytes. Concentrating records fills larger consumer batches; the RSS increase is not the native iterator alone. Both distributions validated and restored all records and media. These measurements preceded the follow-up fresh-migration locator-cache optimization.

The existing iterator still enforces its 100,000-entry ceiling per shard. An adversarially concentrated collection can hit that ceiling despite a low total compared with the nominal 256-shard capacity; fail-closed behavior is intentional. Do not infer full-audit or restore cost from first-page latency. Retain the current explicit layout: these measurements do not establish that a persistent lookup index would reduce end-to-end verification costs enough to justify its crash-consistency and rebuild burden.

## Fresh-migration performance receipt

The final Linux run at `94b5fe3` migrated 100,001 synthetic entries in 84,737 ms (26.719508 CPU seconds; 27,258,880-byte peak RSS). Its full exact-byte inspection took 44,375 ms, with a 2 ms first page scanning 393 entries over a 256-page collection. The separate 4 GiB copy took 21,708 ms with 22,405,120-byte peak RSS. These fixtures measure storage behavior, not domain parsing.

The preceding [Linux run at `82e5a14`](https://github.com/kujolang/assetworks/actions/runs/35911417060) recorded migration at 108,984 ms and 71.333055 CPU seconds. The follow-up restores cached native collection locators for fresh migrations while retaining resume-only conflict and final-count verification. Both runs verified exact bytes. Hosted-runner storage and scheduling varied (including slower final large-file copying), so the receipts support retaining the optimization without establishing a controlled percentage improvement or production SLA.
